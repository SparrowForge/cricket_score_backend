01 Batting

Runs are the base. Boundaries add a little on top, a milestone rewards a substantial innings for the format, a rate adjustment measures the knock against what the match itself was scoring at, and a contribution point credits the batter's share of the team's runs.

Rate adjustment

expected = balls_faced × match_run_rate ÷ 6 adjustment = clamp((runs_scored − expected) × 0.5, −8, +8)

The match run rate spans both innings, so par is what the game itself was scoring at. A batter who crawled below par loses points, and that loss is real — it is not floored away.

Contribution point

contribution = runs_scored ÷ overs_per_innings

Rewards players who contribute a significant share of the team's runs relative to match length. Unlike other metrics, this is uncapped and reflects the actual contribution ratio. A 50 in a 20-over match yields 2.5 points; 100 in a 50-over match yields 2.0 points — same fraction, same recognition across formats.

Examples: T20 (20 overs): 20 runs = 1.0 pt, 40 runs = 2.0 pts, 60 runs = 3.0 pts. ODI (50 overs): 50 runs = 1.0 pt, 100 runs = 2.0 pts, 150 runs = 3.0 pts.

Dismissed-batter value

For each wicket, the runs the batter had made at the moment of dismissal × 0.2, capped at +4 for that wicket, then summed. Removing a set batter is worth more than removing a tail-ender — but one huge scalp cannot dominate the innings. Run-outs and retirements are excluded, since the bowler did not earn them.

04 Bonuses & the winning multiplier

Applied after the three streams above, strictly in this order — the multiplier lands last, so it lifts the flat bonuses too.

Order of application — updated
StepApplied toEffect
1Player of the match+3

total = (batting + bowling + fielding + potm_bonus) × win_factor

Changed in this version

Removed: +2 winning team bonus. Every participating player on the winning team previously received a flat +2 points. This has been removed; the winning team now receives only the 1.1× multiplier on their base score.

Why: Simplified logic and eliminated double-bonus confusion. The 1.1× multiplier adequately rewards the winning team.

The award is settled before it is paid

The +3 must never decide who wins it. Selection ranks on the three performance components only — not the total, which already carries the winning-side multiplier. A player named by the scorer on the finalize screen always wins; the automatic pick applies only when nobody was named.

05 Signs

Each stream keeps its own sign. A batter who crawled well below par, or a fielder who shelled catches, genuinely cost their side — and that has to survive into the total rather than being floored away stream by stream.

Only the final figure is clamped to zero, and only for display in leaderboards.

06 Recent changes

Contribution point added

New component: runs_scored ÷ overs_per_innings

Rewards batters who contribute a significant share of the team's run total. This is uncapped and scales proportionally across formats — a 50 in a 20-over match and a 125 in a 50-over match both yield 2.5 points.

Impact: Higher-scoring batters gain additional points. In shorter formats the effect is more pronounced per run, which correctly reflects the greater value of each run when there are fewer overs to score them in.

Format-dependent batting milestones

Changed: Milestone thresholds now scale with overs per innings.

  • 1-20 overs: 1.5×O (+4), 2×O (+8), 2.5×O (+12), 3×O (+16)
  • 21+ overs: 1×O (+4), 1.4×O (+8), 1.6×O (+12), 2×O (+16)

Old formula: Absolute thresholds — 4×O, 6×O, 8×O, 10×O

Impact: Better format-appropriate rewards. A 50 in a 5-over game is now recognized as +4, whereas a 100 in a 50-over match is +16, making thresholds fairer across formats.

Removed winning team flat bonus

Changed: Removed the +2 points for every player on the winning team.

Old formula: Batting + bowling + fielding + 2 (if winner) + 3 (if POTM) × 1.1

New formula: Batting + bowling + fielding + 3 (if POTM) × 1.1

Impact: Simpler calculation, no double bonus confusion. Winning team still receives 1.1× multiplier on base score.

Historical data recalculation

Action required: All previously completed matches must be recalculated with the new formula. Use:

node scripts/recalculate-mvp.js

This script rebuilds MVP points for all completed matches and updates tournament and career stats. It is idempotent and can be run safely multiple times.

07 Recalculating

The formula derives entirely from stored ball-by-ball data, so changing it means re-running the build for every completed match. It is idempotent — running it twice produces identical figures, because each pass rebuilds rather than accumulates.

StatsService.recalculateMvp(matchId) // per completed match node scripts/recalculate-mvp.js // all completed matches

Do not use finalizeMatch to replay

finalizeMatch() also calls notifyFollowers(), and the notifications table has no unique constraint — replaying it would send every follower a duplicate "match finished" alert for a game they were told about days ago. recalculateMvp() rebuilds points and the tournament and career rollups, and nothing else.

This rewrites live figures. Every player's MVP number and every leaderboard position moves. Verify inside a rolled-back transaction (BEGIN … ROLLBACK) before writing to production.
